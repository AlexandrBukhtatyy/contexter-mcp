# mcp-context — MCP-сервер контекста задачи

Сервер отдаёт агенту контекст по репозиторию: фрагменты документации (Markdown, ADR, пользовательские истории), места в коде (TS/JS и Go) и контракты API (OpenAPI, AsyncAPI) — вместе со связями между ними. Агент находит нужный раздел документации, а не читает файлы целиком; перед правкой файла узнаёт, что прочитать и кто ещё зависит от этого файла, в том числе без импорта (через каналы очереди и API).

Что уже есть: поиск по документации и коду, связи документации с кодом, контрактами и тестами, отчёт о расхождениях и главный инструмент `get_task_context` — пакет контекста под задачу в пределах бюджета токенов. Поиск по смыслу подключается через свой сервис эмбеддингов (см. «Поиск по смыслу»), особенности проекта — своими экстракторами в `.mcp/extractors/` (см. «Свой экстрактор»). Обновления индекса без команды пока нет: после правок запускается `index`.

Сервер только читает репозиторий: индекс лежит в `.mcp/cache/` индексируемого репозитория и пересобирается из исходников в любой момент.

## Где живёт пакет

План помещает сервер в `tools/mcp-context/` внутри монорепозитория. Здесь он — отдельный репозиторий: так решено, чтобы разработка сервера не задевала монорепозиторий. Индексируемый репозиторий передаётся параметром `--root`, его настройки и индекс лежат в его каталоге `.mcp/`:

| Что | Где |
| --- | --- |
| Код сервера | этот репозиторий |
| Настройки | `<репозиторий>/.mcp/context.yaml` — можно коммитить |
| Личные настройки | `<репозиторий>/.mcp/context.local.yaml` — поверх общих, не коммитить (например, свой сервис эмбеддингов) |
| Индекс | `<репозиторий>/.mcp/cache/index.sqlite` — не коммитить, пересобирается |
| Эталонный набор задач | `<репозиторий>/.mcp/eval/tasks.jsonl` |

Добавьте `.mcp/cache/` и `.mcp/context.local.yaml` в `.gitignore` индексируемого репозитория — или положите `.mcp/.gitignore` с двумя строками `cache/` и `context.local.yaml`.

## Установка

Нужны Node.js 22.18 или новее и git.

```sh
npm ci
npm run build
```

**Бинарники в зависимостях.** SQLite встроен в Node (`node:sqlite`), Go разбирается собственным сканером на TypeScript, тесты идут на встроенном `node:test`. Модели эмбеддингов в пакете нет: поиск по смыслу обращается к внешнему сервису или своему скрипту (см. «Поиск по смыслу»), ближайшие векторы считаются на JavaScript. Единственный нативный модуль — опциональный `sqlite-vec` (`vec0.dll`/`.so`/`.dylib`), сейчас не используется; сервер работает и без него. Установка вообще без бинарников:

```sh
npm ci --omit=optional
```

Проверить, что бинарников нет:

```sh
find node_modules \( -name "*.node" -o -name "*.wasm" -o -name "*.dll" -o -name "*.so" -o -name "*.dylib" -o -name "*.exe" \)
```

## Быстрый старт

```sh
# собрать индекс (первый раз — полная сборка, дальше — только изменённые файлы)
node dist/cli/main.js index --root /path/to/repo

# состояние индекса и отчёт о документации
node dist/cli/main.js status --root /path/to/repo
node dist/cli/main.js check  --root /path/to/repo

# почему файл обработан так, а не иначе
node dist/cli/main.js explain-file docs/adr/0007-auth-tokens.md --root /path/to/repo
```

Без сборки то же самое запускается из исходников: `node src/cli/main.ts …` (Node сам убирает типы).

Индекс сейчас не обновляется сам: после правок запустите `index` ещё раз — изменения подхватятся за секунды. Наблюдение за файлами — этап 5 плана.

### Команды

| Команда | Что делает |
| --- | --- |
| `index [--full] [--no-embeddings]` | собирает или обновляет индекс; `--full` — пересобрать всё, не глядя на хэши; векторы для поиска по смыслу — если он настроен, `--no-embeddings` — пропустить их в этом прогоне |
| `explain-file <путь>` | какой экстрактор выбран, каким правилом, с какими параметрами и что он извлёк |
| `status [--json]` | коммит и время сборки, разобранные и неразобранные файлы, счётчики проблем |
| `check [--json] [--kind KIND] [--limit N]` | битые ссылки, эндпоинты вне контракта, ссылки на исчезнувшие символы, расхождения контрактов с кодом, операции без тестов, возможно устаревшие разделы, непокрытый код |
| `context "<задача>" [--task-id ID] [--open a.ts,b.go] [--budget N] [--task-history] [--similar-tasks] [--debug] [--as-of-task ID]` | пакет контекста, как его получит агент; `--task-history` и `--similar-tasks` — то же, что параметры `task_history` и `similar_tasks`; `--debug` добавляет в `meta.ranking` счёт и списки кандидатов (вне бюджета); `--as-of-task` повторяет закрытую задачу «как до её начала» — без её истории и без задач, заведённых позже (для сравнения агентов) |
| `eval [--set FILE] [--ids a,b] [--budget N] [--shares 0.4,0.5,0.1] [--k 10] [--json] [--snapshots [--work DIR]] [--explain] [--no-vectors]` | замер на эталонном наборе: полнота файлов и документов, точность (первых пяти мест кода и пяти разделов — то, что агент читает первым; и всего пакета — для справки), размер пакета, 95-й перцентиль времени — рядом с целями плана; для сравнения — поиск отдельно. С `--snapshots` — на коде до задачи (см. «Пакет контекста»); с `--explain` — разбор не вошедшего: место среди кандидатов, списки, место в поиске; с `--no-vectors` — без поиска по смыслу |
| `serve` | MCP-сервер по stdio |
| `calls [--json]` | сводка журнала вызовов сервера (`.mcp/cache/calls.jsonl`): инструменты, ошибки, время, размер пакета, режим поиска, начинал ли агент с `get_task_context`. Журнал включается `log.calls` в конфиге |

Общие параметры: `--root DIR` — корень индексируемого репозитория (по умолчанию текущий каталог), `--db FILE` — путь к индексу.

## Подключение к агенту

Сервер работает по stdio и читает готовый индекс, поэтому сначала соберите индекс командой `index`.

**Claude Code** — файл `.mcp.json` в корне индексируемого репозитория (или `claude mcp add`):

```json
{
  "mcpServers": {
    "context": {
      "command": "node",
      "args": ["--disable-warning=ExperimentalWarning", "/path/to/contexter-mcp/dist/cli/main.js", "serve", "--root", "/path/to/repo"]
    }
  }
}
```

**VS Code** — `.vscode/mcp.json`:

```json
{
  "servers": {
    "context": {
      "type": "stdio",
      "command": "node",
      "args": ["--disable-warning=ExperimentalWarning", "/path/to/contexter-mcp/dist/cli/main.js", "serve", "--root", "${workspaceFolder}"]
    }
  }
}
```

### Инструменты

| Инструмент | Когда вызывать | Что возвращает |
| --- | --- | --- |
| `get_task_context` | первым, в начале задачи | пакет в пределах бюджета: `summary`, `docs` (разделы текстом), `code` (места указателями `путь:строка`, по одной записи на файл), `rules` (ADR и правила), `tests` (что запустить), `omitted` (что не поместилось), `meta`; у каждого элемента `why`. Вход — текст задачи и/или `task_id` (ID из трекера или из сообщений коммитов, см. «Задачи»), `open_files`, `budget_tokens`; задачи из истории — по просьбе: `task_history` (файлы коммитов задачи), `similar_tasks` (файлы похожих задач) |
| `search_docs` | в начале задачи, до grep | фрагменты документации и контрактов с текстом, `путь:строка`, причиной попадания и пометкой свежести; эндпоинт вида `GET /barriers/{id}` сразу находит операцию |
| `get_doc` | фрагмента не хватило | оглавление документа или раздел целиком с соседями |
| `search_code` | ищете место в коде | символы TS/JS и Go: сигнатура, комментарий, `путь:строка` |
| `get_symbol` | перед изменением сигнатуры | где объявлен, кто импортирует — и через реэкспорты (для Go — пакет, в том числе из другого модуля `go.work`), чем проверяется, какая документация описывает, какие операции API реализует и кто их вызывает |
| `related` | открыли файл для правки | что прочитать перед правкой, какие контракты реализует, чем проверяется, скрытые зависимости через каналы и API, импорты, файлы того же пакета Go, совместные правки; для операции и канала API — обработчик, клиент, вызывающие, тесты, публикующие и читающие |
| `index_status` | ответы выглядят неполными | состояние индекса; с `path` — каким экстрактором и правилом обработан файл |

Промпт `start-task` (аргумент `task` — текст задачи или её ID) — готовая инструкция агенту: сначала `get_task_context`, потом код по ссылкам, перед правкой — `related`, после — тесты из пакета.

Ресурсы: `docs://toc` — карта документации по типам, `docs://{+path}` — документ целиком (например, `docs://docs/adr/0007-auth-tokens.md`).

Тексты в ответах — цитаты из репозитория с указанием источника. Сервер помечает их как данные: инструкции внутри них агент исполнять не должен.

## Конфиг `.mcp/context.yaml`

Конфиг необязателен: без него работают настройки по умолчанию. Ошибка в конфиге называет файл, строку и ключ, например `.mcp/context.yaml:5:13: extractors.rules.0.use: неизвестный экстрактор «markdwn»; доступны: …` — сервер не стартует молча с умолчаниями. Пример — конфиг учебного репозитория [test/fixtures/repo/.mcp/context.yaml](test/fixtures/repo/.mcp/context.yaml).

**Личные настройки** — `.mcp/context.local.yaml` поверх общего конфига, не для git. Вложенные разделы сливаются, значения и списки из личного файла заменяют общие: `context: { budget_tokens: 8000 }` меняет только бюджет. Типичный случай — поиск по смыслу у того, у кого есть локальная модель, при общем конфиге без него. Ошибка в личном файле называет его самого.

```yaml
version: 1

# Пути, которые не индексируются, сверх .gitignore (glob).
exclude: [".beads/**", ".cache/**"]
max_file_bytes: 4000000

# Свои экстракторы: ES-модули относительно корня репозитория.
plugins: ["tools/mcp/csv-extractor.mjs"]

# Внешние пакеты из node_modules: документация и типы библиотек, которыми пользуется код.
# from — каталог, из node_modules которого импортирует код; include — какие файлы пакета брать.
packages:
  - { name: "@reformer/ui-kit", from: "stacks/ts/apps/admin" }
  - name: "@reformer/core"
    from: "stacks/ts/apps/admin"
    include: ["package.json", "README.md", "docs/**/*.md", "**/*.d.ts"]   # по умолчанию

extractors:
  # Правила проверяются сверху вниз, срабатывает первое подошедшее.
  rules:
    - match: { path: "stacks/ts/packages/api-client/src/generated/**" }
      use: code
      options: { comments: false }
    - match: { path: "**/*.md", frontmatter: { type: adr } }
      use: markdown
    - match: { path: "**/*.json" }
      use: skip
  # Экстрактор по расширению, если правило не подошло.
  defaults: { ".mdx": markdown }

documents:
  # Тип документа по пути, если в шапке нет type. Тип фильтрует search_docs.
  types:
    - { path: "docs/adr/**", type: adr }
  # Статус по регулярному выражению в начале документа (группа 1), если в шапке нет status.
  status:
    - { path: "docs/adr/**", regex: "^\\|\\s*Статус\\s*\\|\\s*([A-Za-z]+)" }
  status_map: { отменён: superseded }
  # Документы с этими статусами не попадают в выдачу (только с include_hidden).
  hidden_statuses: [deprecated, superseded]
  # Ссылки на документы по идентификатору в тексте.
  id_refs:
    - { pattern: "ADR-(\\d{4})", path: "docs/adr/$1-*.md" }

chunking: { min_tokens: 80, target_tokens: 600, max_tokens: 1000 }

links:
  ambiguous_limit: 5     # имя символа, которое встречается чаще, связью не считается
  min_symbol_length: 4

# Роли строковых ключей в коде для связей с контрактами.
keys:
  roles:
    - { kind: channel, path: "stacks/go/apps/worker/**", context: "^boot\\.Env$", value: "^(?!worker-)[a-z][a-z0-9.>*-]*$", role: subscribe }
    - { kind: channel, path: "stacks/ts/apps/api/src/modules/events/**", value: "^events\\.", role: publish }

history:
  enabled: true
  max_commit_files: 30   # коммиты крупнее не считаются совместной правкой
  min_cochange: 2
  blame: true            # даты строк для проверки свежести

# Пакет контекста (get_task_context).
context:
  budget_tokens: 6000                         # бюджет по умолчанию
  shares: { docs: 0.4, code: 0.5, rules: 0.1 }  # доли бюджета; неиспользованное переходит дальше; документы из задачи — вне долей
  rule_types: [adr, rule]                     # типы документов, которые идут в rules
  weights:                                    # множители места по пути
    - { path: "docs/plans/traceability.md", weight: 0.3 }
  max_expansion: 24                           # сколько кандидатов добавляет расширение по связям
  tasks:                                      # задачи в пакете без просьбы агента (параметры task_history, similar_tasks)
    history: false                            # файлы из коммитов задачи по task_id или номеру в тексте
    similar: false                            # файлы похожих задач и коммитов из истории

# Поиск по смыслу (см. «Поиск по смыслу»). По умолчанию выключен.
embeddings:
  provider: http                              # none | http | command | stub
  url: http://localhost:11434/v1/embeddings   # http: Ollama, llama.cpp, vLLM, LM Studio, TEI или удалённый сервис
  model: embeddinggemma
  format: openai                              # openai (/v1/embeddings) | ollama (/api/embed)
  api_key_env: EMBEDDINGS_API_KEY             # http: имя переменной окружения с ключом; ключ в конфиг не пишется
  # command: [node, .mcp/embeddings/embed.mjs]  # свой скрипт вместо http
  query_template: "task: search result | query: {text}"   # подсказки модели (здесь — EmbeddingGemma)
  document_template: "title: {title} | text: {text}"
  dimensions: 256                             # необязательно: обрезать вектор (Matryoshka)
  batch: 64
  targets: [docs, code]                       # разделы документации и символы кода

# Журнал вызовов сервера в .mcp/cache/calls.jsonl — для разбора пилота (сводка — команда calls).
log:
  calls: true                                 # по умолчанию выключен
  task_text: false                            # тексты задач и запросов не пишутся — только их длина

# Задачи (см. «Задачи»): откуда брать, как узнать номер задачи в коммите.
tasks:
  sources: [beads, git]                       # по умолчанию — beads, если есть .beads/issues.jsonl, и git
  id_pattern: "\\bproj-[a-z0-9]+(?:\\.[a-z0-9]+)*\\b"   # по умолчанию — по ID трекера или найденный в коммитах
  git:
    commits_without_id: true                  # коммит без номера задачи — отдельное «изменение»
    max_commits: 5000                         # сколько последних коммитов разбирать

# Намеренные исключения из отчёта check: проблема скрыта, счётчик с причиной остаётся.
checks:
  ignore:
    - { kind: broken-endpoint, value: "^(GET|HEAD) /(livez|readyz)$", reason: "health-пробы вне контракта (ADR-0008)" }
    - { kind: broken-endpoint, path: "docs/plans/**", reason: "планы описывают будущие эндпоинты" }
```

### Условия `match`

Условия соединяются по «и».

| Условие | Что проверяет |
| --- | --- |
| `path` | путь по glob-шаблону |
| `frontmatter` | значения полей шапки Markdown |
| `has_key` | ключ верхнего уровня в JSON или YAML |
| `content` | регулярное выражение по первым 50 строкам |

Порядок выбора экстрактора: поле `extractor` в шапке файла → первое подошедшее правило → встроенные правила (файл с ключом `openapi`/`swagger` — `openapi`, с ключом `asyncapi` — `asyncapi`) → экстрактор по расширению → файл пропускается. Проверить выбор: `explain-file <путь>` или `index_status` с `path`.

Файл переиндексируется, когда изменилось его содержимое, выбранный экстрактор, версия экстрактора или параметры. Поэтому правка правила пересчитывает только файлы, для которых выбор изменился.

### Роли ключей

Связь контракта с кодом строится по строковым литералам: `operationId` операции и адрес канала ищутся в коде как строки. Роль литерала (`implements`, `calls`, `publish`, `subscribe`, `mention`) задаёт первое подошедшее правило `keys.roles`:

- `kind` — `operation` или `channel`;
- `path` — glob файла;
- `context` — регулярное выражение по месту литерала: `ApiOperation.operationId` (свойство объекта в вызове), `boot.Env` (аргумент вызова), `DEVICE_COMMAND_SUBJECT` (константа), `Subject` (поле составного литерала Go);
- `value` — регулярное выражение по самому литералу.

Встроенное правило: литерал в свойстве `operationId` реализует операцию. Литерал с подстановкой NATS (`events.>`) считается подпиской. Без подходящего правила роль — «упоминает». Адрес, собранный из частей (`` `events.${kind}` ``, `"events.%s"`), записывается как неразрешённый, и связь по нему не строится: его долю показывает `index_status`.

## Экстракторы

| Экстрактор | Что делает |
| --- | --- |
| `markdown` | фрагменты по заголовкам: короткий раздел присоединяется к предыдущему, длинный делится по блокам; блок кода остаётся с абзацем, большая таблица делится по строкам с повтором заголовка |
| `code` | TS/JS через TypeScript Compiler API: функции, классы и методы (с декораторами в сигнатуре), интерфейсы, типы, константы, комментарии, импорты, строковые ключи. Параметры: `comments`, `test_pattern`, `keys` |
| `code-go` | Go собственным сканером: функции, методы `Type.Method`, структуры, интерфейсы с методами, константы и переменные пакета, doc-комментарии, импорты пакетов, строковые ключи. Тесты помечаются, сгенерированный код (`// Code generated … DO NOT EDIT.`) — без комментариев |
| `openapi` | фрагмент на операцию и на компонент; текст — исходный YAML, для поиска собирается описание; метод, путь и `operationId` хранятся отдельно |
| `asyncapi` | фрагмент на канал, операцию, сообщение и схему; адрес канала хранится отдельно |
| `bruno` | коллекции Bruno (`.bru`): запрос — символ `http-test` с сигнатурой `МЕТОД /путь`, тесты `test("…")` из скриптов — символы `test`, блок `docs` — комментарий; окружения и настройки коллекции пропускаются |
| `skip` | файл в индекс не попадает |

### Тесты

Тестовые файлы (`test_pattern` экстрактора `code`, `_test.go`, `.bru`) индексируются с пометкой «тест» и в поиске идут ниже основного кода. Файл TS/JS из каталога тестов, в котором нет ни одного тест-кейса и имя которого не тестовое (не `.spec`, `.test`, `.e2e-spec`), — вспомогательный код тестов: `tests/unique.ts`, `tests/lane.ts`, модули отчёта. Его правят как обычный код, поэтому он ищется и попадает в пакет наравне с основным кодом, и разделы, которые его описывают, проверяются на свежесть.

Кроме символов тестового файла:

- **тест-кейсы** `describe`/`it`/`test` (jest, vitest, node:test, Playwright `test.describe`) — символы `suite` и `test` с цепочкой названий «набор › тест»; ищутся `search_code` с `kind: ["test"]`;
- **тесты Go:** `TestXxx`, `BenchmarkXxx`, `FuzzXxx`, `ExampleXxx` — символы `test`; подтесты `t.Run("…", …)` — символы с цепочкой «TestXxx › подтест › вложенный», литералы внутри подтеста приписываются ему. Табличные подтесты `t.Run(tc.name, …)` раскрываются в случаи таблицы — по полю `name: "…"`, по позиции поля в строках `{"…", …}`, по литералам среза или ключам словаря в `for … := range`; случай — символ на строке, где он объявлен. Если имена в таблице не литералы (константы, `fmt.Sprint(i)`), случаев нет;
- **ссылки из названия теста:** ID документа по `id_refs` (`ADR-0044`, `US-C11`) и эндпоинт (`GET /me`) связывают документ или операцию с тестом;
- **HTTP-вызовы в тестах:** `request(app).post("/passes")`, `` .get(`/passes/${id}`) `` связывают тест-кейс с операцией контракта (подстановки — параметры пути);
- **сценарии Bruno** связываются с операцией по методу и пути запроса.

`get_symbol` и `related` показывают `tested_by`: тесты, которые импортируют файл (в том числе через реэкспорт), и тесты операций, которые он реализует. Для операции `related` отдаёт `api.tested_by`, для документа — тесты среди `code` с ролью «проверяет». `check` перечисляет операции, к которым не обращается ни один тест.

### Внешние пакеты

Пакеты из `packages` читаются из `node_modules` (ссылки pnpm разворачиваются) и индексируются по путям `<from>/node_modules/<name>/…`: документация получает тип `library`, типы `.d.ts` — символы с комментариями. Импорт пакета из кода (`@reformer/ui-kit`, подпути `exports` вроде `@reformer/ui-kit/fields`) разрешается в его типы, поэтому `get_symbol` по компоненту библиотеки показывает, кто его использует, — через цепочки реэкспортов `index.d.ts`. Имя в документе репозитория сначала ищется среди символов репозитория, в документации библиотеки — среди символов этой библиотеки. Проблемы документации пакетов в `check` не попадают, их код не входит в «непокрытый код», `git blame` для них не запускается. Исходники пакета (`src/`) по умолчанию не берутся — хватает типов; при необходимости добавьте их в `include`.

### Свой экстрактор

Всё, что знает о конкретном проекте (манифест маршрутов, схема БД, формат каталогов), живёт в самом проекте — в `.mcp/extractors/` — и подключается в `.mcp/context.yaml`. Ядро сервера остаётся общим.

```yaml
plugins:                                   # модули, пути от корня репозитория
  - .mcp/extractors/admin-routes.mjs
  - .mcp/extractors/drizzle-tables.mjs
extractors:
  rules:                                   # какие файлы отдать своему экстрактору и с какими параметрами
    - match: { path: "apps/admin/routes.gen.json" }
      use: admin-routes
      options: { title: "Экраны admin" }
    - match: { path: "packages/db/src/schema/**/*.ts" }
      use: drizzle-tables
entities:                                  # как документы и задачи ссылаются на объявленные сущности
  table: { dotted: true, title: "таблица" } # `passes` и `passes.organization_id` — ссылки на таблицу passes
  screen: { title: "экран" }               # `/users/:id`
```

Модуль экспортирует по умолчанию объект `{ name, version, description?, optionsSchema?, extract(file, options, kit) }`:
- `file` — `{ path, text (LF, без BOM), hash }`;
- `options` — параметры из правила; `optionsSchema` — схема zod (`kit.z`) или объект с `safeParse`, без неё параметры не проверяются;
- результат — `{ kind: "document", document }`, `{ kind: "code", code }` или `{ kind: "skip", reason }`. Типы записей — в [src/extractors/types.ts](src/extractors/types.ts).

`kit` — функции ядра, чтобы проекту не ставить зависимости:

| Функция | Что делает |
| --- | --- |
| `kit.chunk({ id, headingPath, ordinal, kind, text, lineStart, lineEnd, refs?, searchText?, searchOnly?, api?, entities? })` | раздел документа: токены и хэш считаются сами. `searchText` — дополнительные слова для поиска (ищутся вместе с `text`); `searchOnly: true` — искать только по `searchText`, когда `text` нельзя искать как есть (сырой YAML, JSON). Агент всегда получает `text`; поиск по смыслу считается по заголовку и `text` |
| `kit.ids().take(id)` | уникальные id в пределах файла (повтор — `-2`, `-3`) |
| `kit.slugify(text)`, `kit.frontmatter(text)` | якорь из заголовка; YAML-шапка Markdown |
| `kit.run(name, file, options?)` | встроенный экстрактор (`markdown`, `code`, `code-go`, `openapi`, `asyncapi`, `bruno`): свой экстрактор дополняет его, а не заменяет |
| `kit.z` | zod для `optionsSchema` |

**Сущности** — таблицы, экраны, команды: то, на что ссылаются по имени. Экстрактор объявляет их в `code.entities` (объявление в коде, с `symbolId` символа) или в `chunk.entities` (объявление в документе): `{ kind, name, line, symbolId? }`. Дальше всё общее:
- строка в обратных кавычках в документации с именем сущности — связь «упоминает» на место объявления (видно в `related`, расширяет пакет);
- имя в обратных кавычках в задаче — точное совпадение и опорная точка пакета;
- поле шапки документа со списком имён (`documents.header_links`, см. «Шапка документа») — связь, а неизвестное имя — проблема `check`;
- `index_status` показывает число сущностей по видам, по файлу — объявленные в нём; `related` по файлу — `declares`.

Пример — таблицы из схемы Drizzle поверх встроенного `code`:

```js
// .mcp/extractors/drizzle-tables.mjs
export default {
  name: "drizzle-tables",
  version: 1,
  async extract(file, options, kit) {
    const res = await kit.run("code", file);          // символы и импорты — как у обычного TS
    if (res.kind !== "code") return res;
    const lineAt = (i) => file.text.slice(0, i).split("\n").length;
    const entities = [...file.text.matchAll(/\bpgTable\(\s*["']([a-z_][a-z0-9_]*)["']/g)].map((m) => {
      const line = lineAt(m.index);
      const symbol = res.code.symbols.find((s) => s.lineStart <= line && line <= s.lineEnd);
      return { kind: "table", name: m[1], line, symbolId: symbol?.id ?? null };
    });
    return { kind: "code", code: { ...res.code, entities } };
  },
};
```

Экраны из JSON-манифеста маршрутов — документ с разделом на маршрут: `kit.chunk` с текстом «Экран `/users/:id` — «Пользователь», вкладки …», `refs: [{ kind: "ident", value: "UserDetailPage", line }]` (связь на компонент страницы строит общий шаг связывания) и `entities: [{ kind: "screen", name: "/users/:id", line }]`. Рабочие примеры — в тестах: [test/fixtures/plugins/](test/fixtures/plugins/).

Версию модуля менять не обязательно: хэш его исходника входит в хэш параметров, и правка модуля переиндексирует его файлы. Экстрактор не знает про базу: он получает файл и параметры и возвращает записи, связи с другими файлами считает общий шаг связывания.

## Шапка документа

Шапка (frontmatter) необязательна, но даёт самые надёжные сигналы:

```yaml
---
type: guide            # guide | adr | rule | api | runbook | … — фильтр search_docs
status: active         # статус из hidden_statuses скрывает документ из выдачи
covers:                # какой код описывает документ — связь с высоким доверием
  - apps/checkout/src/store/**
owner: team-checkout
extractor: markdown    # необязательно: экстрактор для этого файла в обход правил
---
```

Без шапки тип берётся из `documents.types` по пути, статус — из `documents.status`.

Свои поля шапки со ссылками превращаются в связи правилами `documents.header_links`:

```yaml
documents:
  header_links:
    - { field: "related.adr" }                              # значения — ID документов по documents.id_refs
    - { field: "related.flows", path: "docs/flows/$1.md" }  # slug → путь файла
    - { field: "entities", entity: table }                  # имена сущностей (см. «Свой экстрактор»)
```

Поле через точку — вложенное (`related.adr`); значение — строка или список. Связь идёт от первого раздела документа (`related` показывает её у документа и у цели, пакет расширяется по ней). Значение, которое не разрешилось, — проблема `broken-header-ref` в `check`.

## Как строятся связи документации с кодом

| Источник | Пример в тексте | Доверие |
| --- | --- | --- |
| `covers` в шапке | `covers: [apps/api/**]` | высокое |
| Markdown-ссылка на файл | `[сервис](../../apps/api/slot.service.ts)` | высокое |
| Путь в обратных кавычках | `` `stacks/go/apps/worker/internal/dispatch` `` | высокое; только имя файла (`` `slot.service.ts:12` ``) — среднее |
| Шаблон путей | `` `apps/worker/**` `` | среднее |
| Имя символа | `` `SlotService.resetSlot` ``, `` `dispatch.NewHandler` ``, `` `Type.Method()` `` | высокое, если имя уникально; иначе ближайший по пути — среднее |
| Расположение | `README.md`, `CLAUDE.md`, `docs/` внутри пакета | среднее |
| Эндпоинт | `GET /barriers/{id}` | высокое; конкретное значение на месте параметра — среднее |
| Адрес канала | `` `events.incident` `` | высокое |
| Идентификатор документа | `ADR-0044` (по `id_refs`) | высокое |

Простое слово в нижнем регистре (`` `status` ``) символом не считается: такая связь была бы шумом. Имя без класса, которое совпало только с методом, а в коде служит ключом данных (поле DTO, ключ объекта, тег `json:"…"` в Go), тоже не связывается: `` `organizationIds` `` в описании payload — поле, а не метод `TenantContextService.organizationIds`. Вызов со скобками (`` `organizationIds()` ``) ведёт на метод.

## Пакет контекста (`get_task_context`)

Сервер не вызывает LLM: пакет собирается поиском по готовому индексу, поэтому быстро и воспроизводимо — один и тот же запрос на одном индексе даёт один и тот же пакет.

1. **Разбор задачи.** Из текста берутся пути (`slot.service.ts:21`), идентификаторы (`` `SlotService.resetSlot` ``, `parseGSMFrame`, `dispatch.NewHandler()`), эндпоинты (`GET /slots/{id}`), тексты ошибок, ID документов (`ADR-0044`) и задач (`proj-104`). С `task_id` текст берётся из источников задач (см. «Задачи»).
2. **Опорные точки.** Открытые файлы, файлы и символы, названные в задаче, обработчики названных эндпоинтов; с `task_history` — файлы из коммитов задачи и её эпика.
3. **Списки кандидатов.** Точные совпадения; документация к опорным файлам; поиск по словам — по заголовку задачи, по всему тексту, по тексту ошибки; с `similar_tasks` — файлы похожих задач и коммитов из истории (похожие задачи правят похожие места); пользователи имени из задачи — файлы, которые его импортируют (не больше 12 на имя, иначе имя слишком общее; помогает, когда правят места использования, а объявление во внешнем пакете); расширение по связям на один шаг (раздел → код, код → раздел, операция → обработчик); соседи — файлы, которые меняются вместе (история git), и файлы пакета, связанные импортом; ближайшие по смыслу разделы и символы — если настроен поиск по смыслу.
4. **Ранжирование.** Списки сливаются по местам (reciprocal rank fusion; места считаются отдельно для документов и для кода), затем поправки: близость к опорным файлам, библиотеки и сгенерированный код ниже, ADR со статусом proposed ниже, веса путей из `context.weights`.
5. **Упаковка.** Документы, найденные точным совпадением (ID или путь из задачи, операция контракта), идут первыми, вне долей, — до трёх. Тест, названный в задаче, — первым в разделе тестов. Остальной бюджет делится долями `context.shares` между документацией, кодом и правилами; в первом проходе — один раздел на документ, остаток — в общем порядке кандидатов. Длинный раздел обрезается (`truncated`, целиком — `get_doc`), места в коде группируются по файлу (`also`), тесты — что импортирует выбранный код, тесты его операций, тесты рядом (`foo_test.go`, `foo.spec.ts`). Итоговый ответ проверяется по токенам: пакет никогда не больше бюджета, лишнее уходит в `omitted`.

Поиск по словам учитывает и видимые тексты кода — подписи JSX и строки с текстом (сообщения, тексты ошибок): задача «кнопка „Пригласить гостя“» находит компонент, который её рисует.

`eval` считает метрики плана на эталонном наборе. Задача из набора прогоняется без истории самой задачи и без задач, созданных позже неё: иначе коммиты с её ID подсказали бы ответ. На текущем коде из похожих исключаются и «изменения» её коммитов-решений (`commits` набора), а если даты задачи нет ни в одном источнике, «позже» считается от самого раннего коммита-решения.

Запись набора — объект JSON: `id`, `task` (текст задачи), `files` (файлы, которые задача меняет), `docs` (документы, которые нужно прочитать), необязательные `type`, `note`, `draft: true` (черновик, ответы не проверены), `reviewed` (кто проверил ответы: `human` или `claude`), `commits` (коммиты-решения задачи) и `before` (пути до задачи, см. ниже). Объекты пишутся по одному в строке или многострочно. Файлы и документы, которых нет в индексе, в метриках не учитываются.

**Замер на коде до задачи** (`eval --snapshots`). На текущем коде решение закрытой задачи уже лежит в репозитории, и поиск находит его реализацию — оценка завышена. С `--snapshots` каждая задача меряется на родителе самого раннего из своих `commits`: в таком снимке нет ни кода решения, ни его коммитов, а задачи beads — только заведённые к тому времени. Задачи без `commits` пропускаются.

- Пути в `files` и `docs` записываются по текущему коду. Путь на момент до задачи выводится из истории переименований (`git log --follow`). Файл, который создало само решение, в полноту не входит: в снимке его ещё нет, он показывается отдельно. Если код перенесли в другой файл, а не переименовали файл, пути до задачи задаются явно: `"before": {"files": ["…"], "docs": ["…"]}`.
- Снимки — одна копия репозитория в `.mcp/cache/snapshot` (или `--work DIR`): `git clone --shared`, исходный репозиторий только читается. Копия переключается с коммита на коммит по времени, индекс обновляется по изменившимся файлам. Конфиг — текущий `.mcp/context.yaml` вместе с `.mcp/context.local.yaml`: мерится нынешняя настройка. На монорепозитории в пару тысяч файлов копия с индексом занимает около 100 МБ; каталог можно удалить, следующий прогон создаст его заново.
- Внешние пакеты (`packages`) в снимке не индексируются: `node_modules` не хранится в git.

Ограничение честного режима на текущем коде: совместные правки (`cochange`) считаются по всей истории, включая коммиты самой задачи. Это слабая подсказка: соседство учитывается только при двух и более общих коммитах. На снимках этого нет — история кончается до решения.

`eval --no-vectors` мерит без поиска по смыслу, даже если он настроен, — для сравнения. На снимках векторы считаются при индексации каждого снимка только для изменившихся текстов; поставщик берётся из конфига исходного репозитория.

## Задачи

Задачи дают пакету три вещи: текст по `task_id`, файлы задачи (из коммитов с её номером) и «похожие задачи» — файлы, которые правили в похожих задачах раньше. Трекер для этого не обязателен: хватает истории git. Сервер не ходит в сеть и не хранит ключи — трекер с API подключается своим адаптером.

**В пакет задачи попадают по просьбе.** Текст по `task_id` есть всегда, а файлы — только если агент попросил: `task_history: true` — файлы из коммитов задачи и её эпика (задача уже в работе), `similar_tasks: true` — файлы похожих задач и коммитов. Без просьбы их добавляют ключи конфига `context.tasks.history` и `context.tasks.similar`, по умолчанию выключенные. Если история у задачи есть, но не запрошена, в `meta.on_request` сказано, сколько файлов она добавит. Почему так: в замере на коде до задачи (эталонный набор из 28 задач) похожие задачи меняют полноту меньше чем на пункт — то же находят поиск по словам, связи и поиск по смыслу, а лишние кандидаты стоят места в бюджете.

Источники перечисляются в `tasks.sources` по порядку важности:

| Источник | Откуда задачи |
| --- | --- |
| `git` | Номер задачи в сообщениях коммитов. Задача — все коммиты с этим номером: заголовок — тема первого коммита, описание — сообщения коммитов, дата — первого коммита, файлы — файлы этих коммитов. Коммит без номера — отдельное «изменение» `commit:<хэш>` со своим сообщением и файлами (`tasks.git.commits_without_id`): так похожие правки находятся и в команде без номеров задач. |
| `beads` | `.beads/issues.jsonl` (другой путь — `options.path`). |
| `jsonl` | Файл задач в репозитории в нейтральном формате (`options.path`) — например, выгрузка из любого трекера. |
| свой модуль | `{ use: ".mcp/tasks/x.mjs", options: {…} }` — ES-модуль внутри репозитория, см. ниже. |

По умолчанию (`sources` не задан) — `beads`, если есть его файл, и `git`. Задачи из разных источников сливаются по ID: текст и поля трекера главнее, git добавляет файлы и дату, если трекер её не дал. Коммиты массовых правок (больше 150 файлов) в файлы задачи не входят. Из задачи хранятся только ID, заголовок, описание, тип, статус, родитель и дата создания — авторы и исполнители не сохраняются.

Нейтральный формат — строка JSON на задачу, обязательны `id` и `title`:

```json
{"id": "PROJ-12", "title": "Слот сбрасывается после корзины", "description": "…", "status": "closed", "type": "bug", "parent": "PROJ-1", "created_at": "2026-03-01T10:00:00Z"}
```

**Номер задачи в коммитах** — регулярное выражение `tasks.id_pattern`. Лучше задать его явно. Иначе он выводится: по префиксам ID трекера (`proj-104` → `proj-…`), а без трекера — по коммитам: `PROJ-123` (Jira, YouTrack) и `#123` (GitLab, GitHub) берутся, если номер с таким префиксом есть хотя бы в трёх коммитах и в 2% коммитов. Номерами задач не считаются префиксы ID документов из `documents.id_refs` (`ADR`, `US`), обозначения вроде `UTF-8` и `SHA-256` и номера, которые чаще пишутся с ведущим нулём (`AT-04` — критерий приёмки): трекеры номера нулями не дополняют. Что выбрано и откуда, показывают `status` и `index_status` (раздел `tasks`), там же — сколько задач дал каждый источник и сколько «изменений» без номера.

**Свой адаптер** — ES-модуль с default-экспортом `{ name, load(ctx) }`. `load` получает `root`, `options` из конфига, `log` и уже разобранные коммиты (`commits`: хэш, время, сообщение, файлы) и возвращает массив задач в нейтральном формате (можно `async`). Модуль вызывается при каждой индексации. Если `load` падает (сеть, ключ), индексация идёт дальше без задач этого источника, а ошибка видна в журнале индексации и в `status`; модуль, которого нет или который лежит вне репозитория, — ошибка конфига. Ключи — только из переменных окружения. Заготовка для GitLab Issues (в пакет не входит):

```js
// .mcp/tasks/gitlab.mjs
export default {
  name: "gitlab",
  async load({ options, log }) {
    const token = process.env.GITLAB_TOKEN;
    if (!token) {
      log("gitlab: нет GITLAB_TOKEN — задачи не загружены");
      return [];
    }
    const out = [];
    for (let page = 1; page <= (options.max_pages ?? 20); page++) {
      const url = `${options.url}/api/v4/projects/${encodeURIComponent(options.project)}/issues?state=all&per_page=100&page=${page}`;
      const res = await fetch(url, { headers: { "PRIVATE-TOKEN": token } });
      if (!res.ok) throw new Error(`gitlab: ${res.status} ${res.statusText}`);
      const items = await res.json();
      for (const i of items) out.push({ id: `#${i.iid}`, title: i.title, description: i.description ?? "", status: i.state, created_at: i.created_at });
      if (items.length < 100) break;
    }
    return out;
  },
};
```

```yaml
tasks:
  sources:
    - { use: .mcp/tasks/gitlab.mjs, options: { url: "https://gitlab.example.com", project: "group/app" } }
    - git
  id_pattern: "(?<![\\w&/#])#\\d+\\b"   # у ID вида #123 нет префикса, шаблон задаётся явно
```

Для Jira то же самое: `GET /rest/api/3/search/jql?jql=project=PROJ&fields=summary,description,status,issuetype,parent,created` с ключом из окружения, ID — `issue.key`. Если трекер медленный или недоступен из окружения разработчика, проще выгружать задачи в файл и подключать его источником `jsonl`.

## Поиск по смыслу

Для задач, в тексте которых нет слов из документации и кода («один пункт меню вместо трёх»), сервер может искать по смыслу: разделы документации и символы кода (вид, имя, путь, сигнатура, комментарий, видимые подписи) превращаются в векторы, задача — тоже, и ближайшие по косинусу становятся ещё одним списком кандидатов `vectors`. Модели в пакете нет: векторы считает внешний сервис или свой скрипт, их выбирает раздел `embeddings` конфига.

| `provider` | Что это |
| --- | --- |
| `none` | по умолчанию: поиск по словам и связям |
| `http` | сервис по HTTP — локальный или удалённый. `format: openai` — POST `{model, input: [...]}` → `{data: [{embedding}]}`: Ollama `/v1/embeddings`, llama.cpp, vLLM, LM Studio, text-embeddings-inference; `format: ollama` — `/api/embed`. Ключ — из переменной окружения `api_key_env`, заголовки — `headers` |
| `command` | свой скрипт, например `.mcp/embeddings/embed.mjs` или `embed.py`: процесс запускается один раз, рабочий каталог — корень репозитория |
| `stub` | детерминированная заглушка для тестов |

**Протокол `command`** — по строке JSON через stdin/stdout:

```text
→ {"id": 1, "kind": "query", "texts": ["…"]}          kind: query — текст задачи, document — раздел или символ
← {"id": 1, "vectors": [[0.01, …]]}                   или {"id": 1, "error": "…"}
```

Тексты приходят уже по шаблонам конфига; `kind` — для скриптов, которые ставят подсказки модели сами. Логи скрипта — в stderr, stdout занят протоколом.

**Пример: EmbeddingGemma в локальной Ollama.** На нашем эталонном наборе она оказалась точнее `bge-m3` и `qwen3-embedding:0.6b` и быстрее их. `ollama pull embeddinggemma`, затем в конфиге `provider: http`, `url: http://localhost:11434/v1/embeddings`, `model: embeddinggemma` и подсказки модели в шаблонах:

```yaml
query_template: "task: search result | query: {text}"
document_template: "title: {title} | text: {text}"
```

- **Пересчёт.** Векторы считаются при `index` пачками (`batch`), с повторами при сбое сети, 429 и 5xx. Повторно — только для новых и изменившихся текстов: хэш текста вместе с меткой модели (модель, размерность, шаблоны). Смена модели или шаблона — пересчёт всего. `index --no-embeddings` — пропустить векторы в этом прогоне.
- **Хранение.** Таблица `vectors` в индексе; ближайшие считаются перебором на JavaScript (десятки тысяч векторов — миллисекунды).
- **Запрос.** Сервер и `context` считают вектор задачи тем же поставщиком по конфигу на диске; адрес и ключ сервиса в индекс не пишутся. `search_docs` получает `mode`: `words`, `semantic`, `hybrid` (по умолчанию, если векторы есть).
- **Без модели.** Если сервис недоступен или модель в индексе другая, сервер ищет по словам и связям: причина — в `meta.search` пакета, в ответе `search_docs` и в `index_status` (`search_mode`, `embeddings`). `index` перед векторизацией один раз проверяет сервис: если его точно нет (соединение отклонено, адрес не найден, ответ 4xx — например, нет такой модели), векторы пропускаются одной строкой в журнале, причина — в `embeddings.last_error`; медленный ответ (модель грузится в память) отказом не считается. Векторы изменившихся текстов удаляются до пересчёта: при сбое у раздела нет вектора, а не устаревший. Вектор запроса агента — одна попытка до 15 с; после сбоя минуту запросы идут по словам, не дожидаясь сервиса.
- **Где включать.** Если модель есть не у всех, держите `embeddings` в личном `.mcp/context.local.yaml`, а в общем конфиге — без него.
- **Приватность.** С удалённым сервисом тексты документации и кода уходят на него. Для закрытого кода — локальная модель.

## Проверка документации

`check` и `index_status` показывают:

- битые ссылки на файлы и пути в тексте (пути из `.gitignore` битыми не считаются);
- ссылки на символы, которых нет в коде (`pkg.Func` Go-пакета, `Type.Method()`);
- эндпоинты из документации, которых нет в контракте;
- `$ref` контрактов в никуда;
- операции без обработчика в коде, каналы без кода, без публикующего или без читающего, публикации в адрес вне контракта;
- операции, к которым не обращается ни один тест (нет сценария Bruno, HTTP-вызова в тесте или эндпоинта в названии теста; UI-тест может проверять операцию косвенно);
- возможно устаревшие разделы: код, на который уверенно ссылается раздел, менялся позже раздела (по `git blame`);
- непокрытый код: пакеты и каталоги, на которые не ссылается ни один раздел.

Намеренные расхождения скрываются правилами `checks.ignore`; в отчёте и в `index_status` остаётся, сколько проблем скрыто и по какой причине.

## Разработка

```sh
npm run check        # типы, линтер, тесты
npm test             # только тесты (node:test, запускает .ts напрямую)
npm run build        # сборка в dist/
```

Тесты используют учебный репозиторий [test/fixtures/repo](test/fixtures/repo). История git для него создаётся во временном каталоге при каждом прогоне ([test/helpers.ts](test/helpers.ts)).

Вспомогательные скрипты:

- `node scripts/eval-draft-from-beads.ts <репозиторий>` — черновик эталонного набора из закрытых задач beads и коммитов;
- `node scripts/links-sample.ts <репозиторий>` — выборка связей для ручной проверки.

Весь SQL живёт в [src/store/sqlite/](src/store/sqlite/), остальной код работает с хранилищем через интерфейсы [src/store/types.ts](src/store/types.ts): базу можно заменить, например на графовую.
